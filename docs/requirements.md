# 요구사항 정의서 (Requirements Specification)

- **프로젝트명:** AI 기반 가전제품 이전설치 플랫폼
- **영문명:** Appliance Installation Platform
- **문서 버전:** 1.0
- **작성일:** 2026-10-19
- **개발 단계:** PoC 및 MVP
- **문서 목적:** 서비스 기능, 사용자 권한, 업무 규칙 및 비기능 요구사항을 정의하여 프론트엔드·백엔드 통합 개발의 기준으로 사용한다.

---

## 1. 프로젝트 개요

### 1.1 추진 배경

가전제품의 이전설치 서비스를 이용하려면 고객이 제품 정보, 이전·설치 주소, 설치 환경 등을 직접 설명하고 견적을 확인해야 한다. 설치 조건에 따라 비용이 달라지고, 기사 배정 및 예약 과정에서도 수작업이 발생할 수 있다.

본 프로젝트는 고객이 웹에서 이전설치를 신청하면 AI가 이미지와 입력 정보를 분석하고, 가격 규칙 엔진을 통해 견적을 산출하며, 예약·결제·기사 배정까지 연계하는 통합 플랫폼을 구축하는 것을 목표로 한다.

### 1.2 개발 목표

1. 고객이 가전제품 이전설치를 온라인으로 신청할 수 있도록 한다.
2. 사진과 입력 정보를 기반으로 AI 설치 환경 분석 기능을 제공한다.
3. 관리 가능한 가격 규칙을 이용해 견적을 자동 산출한다.
4. 고객이 견적을 확인하고 예약 및 결제를 진행할 수 있도록 한다.
5. 기사별 서비스 지역, 작업 가능 품목 및 일정에 따라 기사를 배정한다.
6. 관리자가 회원, 기사, 가격 정책, 예약 및 결제 상태를 관리할 수 있도록 한다.
7. 향후 클라우드 배포와 기능 확장이 가능한 구조로 개발한다.

### 1.3 개발 범위

**MVP 포함 범위**

- 고객·기사·관리자 사용자 관리
- 로그인 및 역할별 권한
- 가전제품 및 설치 요청 관리
- 이미지 업로드 및 AI 분석 연계
- 자동 견적 산출
- 견적 조회 및 예약
- 결제 연동 기반 구조
- 기사 배정 및 작업 상태 관리
- 관리자 대시보드
- API 및 업무 처리 로그
- 통합 테스트 및 Docker 기반 개발 환경

**MVP 이후 확장 범위**

- 모바일 앱
- 실시간 기사 위치 추적
- 다국어 및 다국가 서비스
- 고도화된 AI 비용 예측 모델
- 수요 예측 및 동적 가격 책정
- 외부 ERP·회계 시스템 연계

| 형상 관리 | Git |

### 2.3 공통 개발 원칙

1. 프론트엔드와 백엔드는 하나의 Git 저장소에서 관리한다.
2. 각 프로젝트는 독립적으로 빌드하고 실행한다.
3. 프론트엔드와 백엔드 간 통신은 REST API로 처리한다.
4. API 계약은 `docs/api-spec.md`에 정의한다.
5. DB 스키마는 `docs/database.md`와 마이그레이션 파일을 기준으로 관리한다.
6. 모든 비즈니스 규칙은 백엔드에서 최종 검증한다.
7. AI가 기존 코드를 변경하기 전에 관련 문서와 소스를 확인하도록 한다.
8. 테스트하지 않은 기능을 완료된 것으로 보고하지 않는다.

#### 가격 산출 원칙

- 기본 가격과 추가 비용은 관리자가 설정한 활성 가격 정책을 기준으로 계산한다.
- AI가 제안한 설치 조건은 확정된 가격 규칙과 구분한다.
- 고객에게 총액뿐 아니라 주요 산출 항목을 제공한다.
- 동일한 견적을 재조회할 때 확정된 견적 금액이 임의로 바뀌지 않도록 한다.
- 할인, 세금, 취소 수수료 및 추가 작업 비용은 별도의 정책으로 관리한다.
- 가격 정책의 적용 시점과 버전을 기록한다.
- 견적 동의는 가격 확인만 기록하며 예약 확정이나 결제를 자동으로 수행하지 않는다.

## 5. 업무 프로세스

### 5.1 기본 서비스 흐름

1. 고객이 회원가입 및 로그인한다.
2. 이전설치 요청을 작성한다.
3. 제품 및 설치 환경 이미지를 등록한다.
4. 시스템이 이미지와 입력 정보를 분석한다.
5. 부족한 정보가 있으면 고객에게 추가 입력을 요청한다.
6. 가격 규칙 엔진이 견적을 산출한다.
7. 고객이 견적을 확인하고 예약을 요청한다.
8. 시스템이 예약 가능 여부를 검증한다.
9. 고객이 결제를 진행한다.
10. 결제 상태가 검증되면 예약 확정 정책을 적용한다.
11. 시스템이 적합한 기사를 배정한다.
12. 기사가 작업을 수행하고 완료 상태를 등록한다.
13. 고객과 관리자가 완료 내역을 조회한다.

### 5.2 주요 상태 정의

**설치 요청 상태**

- DRAFT: 작성 중
- SUBMITTED: 접수 완료
- ANALYZING: AI 분석 중
- NEEDS_REVIEW: 추가 확인 필요
- QUOTED: 견적 완료
- RESERVED: 예약 확정
- IN_PROGRESS: 작업 진행 중
- COMPLETED: 작업 완료
- CANCELLED: 취소

**예약 상태**

- PENDING: 예약 요청
- CONFIRMED: 예약 확정
- RESCHEDULE_REQUESTED: 일정 변경 요청
- CANCELLED: 취소
- EXPIRED: 예약 만료
- COMPLETED: 완료

**결제 상태**

- READY: 결제 준비
- IN_PROGRESS: 결제 진행 중
- PAID: 결제 완료
- FAILED: 결제 실패
- CANCEL_REQUESTED: 취소 요청
- CANCELLED: 결제 취소 완료
- PARTIALLY_REFUNDED: 부분 환불
- REFUNDED: 전액 환불

상태 변경은 정의된 전이 규칙에 따라서만 허용한다. 예를 들어 취소 완료된 예약이 별도의 재예약 절차 없이 다시 작업 중으로 변경되지 않도록 한다. 결제 상태와 예약 상태는 서로 독립적으로 관리하며, 결제 취소와 환불을 동일한 상태로 취급하지 않는다.

### 5.3 예외 처리

- AI 분석 실패: 오류 기록 후 재시도 또는 수동 검토
- 견적 산출 실패: 예약 진행을 제한하고 원인을 기록
- 예약 슬롯 충돌: 요청을 거절하고 가능한 시간 재조회
- 결제 승인 실패: 예약 정책에 따라 대기 또는 실패 처리
- 결제 결과 수신 지연: 결제 상태 조회 및 대사 처리
- 기사 배정 실패: 관리자에게 재배정 대상 알림
- 이미지 업로드 실패: 오류 안내 후 재시도 지원

## 7. 비기능 요구사항

### 7.1 보안

- 모든 입력값을 서버에서 검증한다.
- 비밀번호는 안전한 단방향 해시 방식으로 저장한다.
- 인증 정보와 비밀키를 소스 코드에 하드코딩하지 않는다.
- 인증 및 권한 검증은 백엔드에서 수행한다.
- 쿠키 인증을 사용할 경우 HttpOnly, Secure 및 적절한 SameSite 설정을 적용한다.
- JWT를 사용하는 경우 만료, 재발급 및 폐기 정책을 정의한다.
- 파일 업로드 시 확장자, 실제 파일 유형, 크기 및 접근 권한을 검증한다.
- 개인정보와 인증 토큰을 로그에 남기지 않는다.
- 운영 환경에서는 HTTPS를 사용한다.
- 관리자 권한 변경 및 결제·환불 등 중요 작업은 감사 로그를 남긴다.

### 7.2 성능

초기 PoC·MVP의 목표이며, 실제 성능은 부하 테스트 결과에 따라 조정한다.

- 일반 API의 응답시간: 정상 부하에서 95백분위 기준 2초 이내를 목표로 한다.
- 주요 목록 조회는 페이지네이션을 적용한다.
- 이미지 업로드와 AI 분석은 일반 API 요청과 분리하고 필요하면 비동기 처리한다.
- DB 연결 풀과 타임아웃을 적절히 설정한다.
- 중복 요청과 동시 예약을 방지한다.

### 7.3 가용성 및 복구

- 애플리케이션 오류를 로그로 기록한다.
- DB 데이터 백업과 복구 절차를 정의한다.
- 외부 AI 및 결제 API의 타임아웃과 실패 처리를 구현한다.
- 재시도는 중복 결제 또는 중복 예약을 유발하지 않도록 설계한다.
- 운영 환경에서는 헬스체크와 장애 알림을 구성한다.

### 7.4 유지보수성

- Controller, Service, Repository 계층을 분리한다.
- DTO와 엔티티를 분리한다.
- 공통 오류 응답 규격을 정의한다.
- API 변경 시 API 명세를 함께 갱신한다.
- DB 스키마 변경은 버전 관리되는 마이그레이션으로 적용한다.
- 비즈니스 규칙과 가격 정책을 코드에 무분별하게 하드코딩하지 않는다.

### 7.5 호환성

- 데스크톱과 모바일 브라우저에 대응하는 반응형 UI를 제공한다.
- 프론트엔드와 백엔드의 시간대 및 날짜 처리 기준을 통일한다.
- API 버전은 `/api/v1` 형태로 관리한다.

## 9. 외부 시스템 연계 요구사항

### 9.1 AI 이미지 분석

- 이미지 저장소와 AI 분석 서비스를 별도 어댑터로 분리한다.
- AI 서비스의 인증키는 환경변수 또는 비밀 관리 시스템으로 관리한다.
- 이미지 분석 요청 및 결과를 추적할 수 있는 식별자를 부여한다.
- 분석 실패, 타임아웃, 사용량 및 비용을 기록한다.
- AI 결과는 검증 전까지 확정된 견적이나 설치 가능 여부로 취급하지 않는다.

### 9.2 결제 서비스

- 결제 사업자 연계 코드를 도메인 로직과 분리한다.
- 서버에서 결제 승인 결과를 검증한다.
- 웹훅은 서명 및 중복 이벤트를 검증한다.
- 결제 요청에는 중복 처리 방지 키를 적용한다.
- 환불 및 결제 취소 결과를 내부 상태와 동기화한다.

### 9.3 클라우드 및 저장소

- 개발 환경에서는 Docker Compose와 로컬 설정을 사용한다.
- 운영 환경의 클라우드 사업자는 별도 아키텍처 검토 후 결정한다.
- 파일 저장소는 S3 또는 Azure Blob Storage로 교체할 수 있도록 추상화한다.
- DB 비밀번호와 API 키는 환경별로 분리한다.

## 10. 테스트 및 완료 기준

### 10.1 테스트 범위

- 단위 테스트: 가격 계산, 상태 전이, 권한 검증
- API 테스트: 요청·응답 및 오류 처리
- DB 통합 테스트: 저장, 조회, 트랜잭션 및 제약조건
- 프론트엔드 테스트: 입력 검증, 로딩 및 오류 상태
- 통합 테스트: React → Spring Boot → PostgreSQL
- 보안 테스트: 권한 없는 데이터 접근 및 입력 검증
- 동시성 테스트: 중복 예약과 중복 결제 요청
- 외부 연계 테스트: AI 및 결제 서비스의 실패 시나리오

### 10.2 MVP 완료 기준

1. 프론트엔드와 백엔드가 하나의 Git 저장소에서 관리된다.
2. React와 Spring Boot가 독립적으로 빌드 및 실행된다.
3. PostgreSQL 연결과 스키마 관리가 정상 동작한다.
4. 회원 인증 및 역할별 권한이 적용된다.
5. 설치 요청을 등록하고 DB에서 조회할 수 있다.
6. 이미지 업로드 및 AI 분석 결과를 확인할 수 있다.
7. 가격 규칙에 따라 견적이 산출된다.
8. 예약 충돌과 중복 결제가 방지된다.
9. 예약·결제·기사 배정의 상태가 일관되게 관리된다.
10. 핵심 성공 및 실패 시나리오에 대한 자동화 테스트가 통과한다.
11. 비밀키가 저장소에 노출되지 않는다.
12. README에 개발 환경 구성과 실행 방법이 기록된다.

외부 AI 및 결제 서비스의 실계정 연동이 완료되지 않았다면 해당 기능은 연동 어댑터와 모의 구현으로 검증하고, 실제 운영 연동 완료와 구분하여 보고한다.

## 12. AI 코딩 에이전트 작업 지침

본 문서는 개발 요구사항의 기준 문서다. AI 코딩 에이전트는 다음 원칙을 따른다.

1. 기능 구현 전에 관련 요구사항 ID를 확인한다.
2. 프론트엔드·백엔드·DB 변경 범위를 먼저 제시한다.
3. API 계약 및 데이터 모델 변경 시 관련 문서를 갱신한다.
4. 기능은 작은 단위로 구현하고 테스트한다.
5. 결제, 인증, 예약 및 개인정보 관련 변경은 보안 관점에서 검토한다.
6. 외부 API의 실계정이나 비밀키가 없는 경우 모의 구현과 실제 연동을 명확히 구분한다.
7. 테스트 결과와 미완료 사항을 작업 보고서에 기록한다.
8. 요구사항에 정의되지 않은 중요 업무 규칙은 임의로 확정하지 않고 질문하거나 제안한다.
